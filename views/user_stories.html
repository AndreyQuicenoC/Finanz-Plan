E-2: Acceso y Autenticación

Sistema seguro de registro y acceso a la plataforma

Esta épica cubre el proceso completo de autenticación, permitiendo a los visitantes convertirse en usuarios registrados de manera segura y sencilla. Incluye formularios de registro, login, recuperación de contraseña y validaciones necesarias para proteger las cuentas.

US-1: Sign-up básico (HU10)

Como visitante de la plataforma
Quiero crear una cuenta con mis datos personales
Para poder ingresar y gestionar mis tareas.

✓ Criterios de Aceptación:
  • Visualización del formulario:
    • Al acceder a /signup se muestran siempre los campos: Nombres, Apellidos, Edad (numérico ≥ 13), Correo electrónico, Contraseña (≥ 8 caracteres, mínimo 1 mayúscula, número y carácter especial) y Confirmar contraseña.
  • Validación en tiempo real:
    • El botón Registrarse permanece deshabilitado hasta que todos los campos sean válidos.
    • Contraseña ≥ 8 caracteres, al menos una mayúscula, una minúscula y un número.
    • Confirmar contraseña coincide.
    • Edad contiene solo dígitos y es ≥ 13.
    • Los mensajes de error se anuncian en una región tooltip y desaparecen al corregir el campo.
  • Envío exitoso:
    • Al presionar Registrarse con datos válidos se muestra un spinner de procesamiento (máx. 3 s).
    • El backend responde HTTP 201 con el id del nuevo usuario.
    • Se emite un toast "Cuenta creada con éxito" y el usuario es redirigido a /login en ≤ 500 ms.
  • Manejo de errores de servidor:
    • Si el correo ya existe, el backend devuelve 409 Conflict y el front muestra "Este correo ya está registrado" sin recargar la página.
    • Cualquier error 5xx muestra un estado genérico "Intenta de nuevo más tarde" y se registra en la consola sólo en modo dev.
  • Persistencia segura:
    • El usuario se guarda en MongoDB con contraseña hasheada usando bcrypt (mín. 10 salt rounds).
    • Se registra la fecha de creación (createdAt) en formato ISO-8601.
✅ Definición de Hecho:
  • Todos los criterios de aceptación se cumplen.
  • Documentación JSDoc añadida; README actualizado con el flujo de registro.
  • Comprobado comportamiento responsivo en 320 px, 768 px y 1024 px mediante Chrome DevTools.
  • Despliegue automático en Vercel (frontend) y Render (API) exitoso.

US-2: Login / Logout (HU11)

Como usuario registrado
Quiero iniciar y cerrar sesión de forma segura
Para acceder a mis tareas y proteger mi información.

✓ Criterios de Aceptación:
  • Visualización del formulario:
    • Al acceder a /login se muestran los campos Correo electrónico y Contraseña más el enlace "¿Olvidaste tu contraseña?".
  • Validación en tiempo real:
    • El botón Iniciar sesión permanece deshabilitado hasta que los campos sean válidos: Correo con formato RFC 5322 y Contraseña.
    • Mensajes de error se anuncian en una región aria-live="polite" y desaparecen al corregir el campo.
  • Autenticación exitosa:
    • Al presionar Iniciar sesión con datos válidos se muestra un spinner de procesamiento (≤ 3 s).
    • El backend responde HTTP 200 con un JSON Web Token válido 2 h.
    • El token se almacena de forma segura (HttpOnly cookie o secure localStorage).
    • El usuario es redirigido a /dashboard en ≤ 500 ms y se muestra un saludo "Hola, Nombre".
  • Persistencia de sesión:
    • Al recargar la página, si el token no ha expirado, el usuario permanece en /dashboard.
    • Acceder a rutas protegidas sin token redirige a /login.
  • Logout:
    • Al seleccionar Cerrar sesión el token se elimina y la cabecera Authorization se limpia.
    • El usuario vuelve a /inicio y se muestra un toast "Sesión cerrada correctamente".
  • Manejo de errores:
    • Credenciales incorrectas → 401 Unauthorized y mensaje "Correo o contraseña inválidos".
    • Cuenta bloqueada → 423 Locked y mensaje "Cuenta temporalmente bloqueada".
    • Errores 5xx → mensaje "Inténtalo de nuevo más tarde" (solo log en consola en modo dev).
  • Seguridad adicional:
    • Se limita a 5 intentos fallidos por IP cada 10 min (respuesta 429 Too Many Requests).
✅ Definición de Hecho:
  • Todos los criterios de aceptación se cumplen.
  • Documentación JSDoc añadida; README actualizado con el flujo de login/logout.
  • Comprobado comportamiento responsivo en 320 px, 768 px y 1024 px.
  • Despliegue automático en Vercel (frontend) y Render (API) exitoso; rutas /login y /logout accesibles vía HTTPS.

US-3: Recuperar contraseña (HU12)

Como usuario que olvidó su contraseña
Quiero restablecerla mediante un enlace enviado a mi correo
Para volver a acceder sin crear una cuenta nueva.

✓ Criterios de Aceptación:
  • Solicitud de recuperación:
    • En /forgot-password se muestra un único campo Correo electrónico con botón Enviar enlace.
    • Al ingresar un correo válido se muestra un spinner (≤ 3 s).
    • El backend responde HTTP 200 y envía un mail con enlace de restablecimiento válido 1 hora y de un solo uso.
    • Se muestra un toast "Revisa tu correo para continuar".
  • Link de restablecimiento:
    • El enlace incluye token seguro (/reset?token=XYZ).
    • Si el token está vigente, lleva a un formulario con Nueva contraseña y Confirmar contraseña.
    • Si el token expiró o fue usado, se muestra mensaje "Enlace inválido o caducado" y opción para reenviarlo.
  • Validación de nueva contraseña:
    • Contraseña ≥ 8 caracteres, con mayúscula, minúscula y número.
    • Confirmar contraseña debe coincidir.
    • Mensajes de error accesibles via aria-live="polite".
  • Restablecimiento exitoso:
    • Al enviar datos válidos backend responde HTTP 200 y actualiza la contraseña (hash bcrypt, 10 salt rounds).
    • El token se invalida inmediatamente.
    • Se emite un toast "Contraseña actualizada" y se redirige a /login en ≤ 500 ms.
  • Manejo de errores:
    • Correo no registrado → 202 Accepted (respuesta genérica para no filtrar cuentas).
    • Errores 5xx → mensaje "Inténtalo de nuevo más tarde" (log solo en modo dev).
✅ Definición de Hecho:
  • Todos los criterios de aceptación se cumplen.
  • Documentación JSDoc añadida; README incluye el flujo de recuperación.
  • Verificado diseño responsivo en 320 px, 768 px y 1024 px.
  • Correo de prueba recibido en un buzón real (ej.: Mailtrap) y enlace operativo.
  • Despliegue en Vercel (front) y Render (API) actualizado; rutas /forgot-password y /reset accesibles vía HTTPS.

E-3: Gestión de Tareas

Herramientas esenciales para gestionar tareas diarias

Esta épica proporciona las funcionalidades core para que los usuarios comiencen a organizar sus tareas inmediatamente después del registro. Incluye creación, listado, edición y eliminación de tareas.

US-4: Crear tarea (HU14)

Como usuario autenticado
Quiero registrar nuevas tareas con título, detalle, fecha y hora
Para organizar mis pendientes.

✓ Criterios de Aceptación:
  • Visualización del formulario:
    • En /tasks/new se muestran los campos: Título (obligatorio, máx. 50 car.), Detalle (opcional, máx. 500 car.), Fecha, Hora y Estado (Por hacer, Haciendo, Hecho).
  • Validación en tiempo real:
    • El botón Guardar permanece deshabilitado hasta que Título, Fecha, Hora y Estado sean válidos.
    • Mensajes de error se anuncian en aria-live="polite" y desaparecen al corregir el campo.
  • Creación exitosa:
    • Al pulsar Guardar con datos válidos se muestra un spinner ≤ 2 s.
    • El backend responde HTTP 201 con el id de la nueva tarea.
    • La tarea aparece inmediatamente en la lista/tablero del usuario en ≤ 300 ms.
  • Persistencia segura:
    • La tarea se guarda en MongoDB con userId, createdAt (ISO-8601) y status.
  • Manejo de errores:
    • Campos obligatorios vacíos → mensaje "Completa este campo" sin recargar la página.
    • Error 5xx → mensaje "No pudimos guardar tu tarea, inténtalo de nuevo" (log solo en modo dev).
✅ Definición de Hecho:
  • Todos los criterios de aceptación anteriores se cumplen.
  • Documentación JSDoc añadida y README actualizado con el flujo de creación de tareas.
  • Verificado diseño responsivo (320 px, 768 px, 1024 px).
  • Despliegue actualizado en Vercel (front) y Render (API); ruta /tasks/new accesible vía HTTPS.

HU14: Registrar transacciones manualmente

Como usuario autenticado

  • Formulario de nueva transacción:

    • Campos obligatorios: Tipo (ingreso/gasto), Monto (numérico positivo), Categoría (dropdown), Fecha, Descripción (máx. 200 caracteres).
